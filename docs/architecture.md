# Lighthouse 첫 버전 설계

## 확정된 사용자 요구

- macOS 전용 데스크톱 앱을 실제 실행 가능한 상태까지 만든다.
- 사진 정리, 빠른 선별, RAW 보정 세 가지를 모두 포함한다.
- Panasonic LUMIX S9의 RW2를 주 대상으로 한다.
- 로컬 우선, 원본 보존, 보정값 별도 저장을 기본으로 한다.

## 첫 버전의 완료 기준

1. 파일·폴더를 가져와 썸네일 그리드로 탐색한다. 같은 파일을 반복 가져오면 중복을 만들지 않는다.
2. 별점 0–5, 채택·제외 표시, 파일명 검색과 필터를 사용한다. 키보드로 사진을 이동·선별한다.
3. 사진을 크게 보고 100% 확대한다. 기준 사진과 현재 사진을 나란히 비교한다.
4. RW2를 실제 RAW 디코더로 읽어 노출·화이트밸런스·색감·명암·선명도를 조절한다. 원본 보기와 초기화, 회전·중앙 비율 크롭을 제공한다.
5. 보정값·분류가 앱 재시작 후 복원된다. 원본 파일을 수정하지 않는다.
6. 선택 사진 또는 필터 결과를 보정한 JPEG로 내보낸다. 크기·품질을 선택하며 기존 파일은 덮어쓰지 않는다.
7. 손상·미지원 이미지와 누락된 원본을 명시적으로 알리고 다른 사진 작업을 계속할 수 있다.

클라우드 동기화, 생성형 제거, 파노라마·HDR 병합(여러 장), 카메라별 자체 색 프로파일, Lightroom 카탈로그 호환은 범위에 포함하지 않는다. 사용자가 직접 실행하는 Google Drive 사진 업로드는 2026-09-27에 범위에 넣었다. 한 장의 RAW를 HDR로 보고 게인 맵 HDR로 내보내는 것은 2026-09-26에 범위에 넣었다(아래 HDR 하이라이트). 자동 마스킹과 자유 크롭 등 승인된 확장은 아래 고급 보정 계약을 따른다.

## 기술 구조

- Swift 6 도구 체인, Swift 6 언어 모드(2026-09-25 전환), macOS 15 이상. Swift Package Manager로 외부 의존성 없이 빌드한다.
  - Swift 6 모드에서는 데이터 경합이 컴파일 오류가 되고, 메인 스레드용으로 추론된 코드가 다른 스레드에서 돌면 실행 중에 멈춘다. 지킬 규칙: 백그라운드 큐에서 도는 `DispatchWorkItem` 클로저에는 `@Sendable`을 직접 붙인다(SDK가 붙여 주지 않아 메인 스레드용으로 추론됨. `queue.async { }`는 SDK가 붙여 준다). 화면 상태는 `DispatchQueue.main.async` 안에서만 바꾼다. 캡처하는 값은 `var` 참조가 아닌 값으로 잡는다. 저장해 둔 클로저를 SwiftUI `Binding`에 그대로 넘기지 말고 `{ set($0) }`처럼 감싼다(`@MainActor` 클로저를 그대로 넘기면 Swift 6.3.2 컴파일러가 멈춘다). 전환 과정은 [검증 기록](verification.md)에 있다.
- SwiftUI 화면과 AppKit 파일 선택·메뉴·키보드 이벤트를 사용한다.
- `LighthouseCore`: Codable 모델, 원자적 JSON 카탈로그 저장, Image I/O 메타데이터·썸네일, Core Image RAW 현상과 JPEG 출력.
- `Lighthouse` 실행 타깃: 메인 액터의 화면 상태와 저장·렌더 작업 조율. 무거운 파일 읽기와 렌더는 백그라운드에서 실행한다.
- 첫 버전 카탈로그는 `Application Support/Lighthouse/catalog.json`에 저장한다. 작은 개인 라이브러리용 단일 JSON이며 대규모 수만 장 성능은 보장하지 않는다. 향후 측정에 따라 SQLite로 이전한다.
- `LIGHTHOUSE_DATA_DIR` 환경 변수로 테스트 데이터를 격리한다. 소스 사진은 원래 위치에 두고 경로를 참조한다.
- 카탈로그 로드 오류를 빈 라이브러리로 간주해 덮어쓰지 않는다. 저장 실패는 사용자에게 표시한다.
- 보정 파라미터와 스키마 버전을 저장하고, 메모리 렌더 결과는 제한된 캐시에 둔다. 다른 사진이나 원본·100% 보기로 바뀐 뒤 도착한 렌더 결과는 적용하지 않는다. 같은 사진을 드래그로 보정하는 동안에는 0.1초 간격으로 그리고 중간 결과를 순서대로 보여 준 뒤 마지막 값의 결과로 끝낸다.
- 편집 미리보기 전용 파이프라인은 최근 현상 결과 2장과 Core Image 중간 계산을 재사용한다. 노출·색온도·틴트가 같으면 RAW를 다시 현상하지 않는다. 최근 미리보기 6장을 기억하고 이동 방향의 다음 사진을 미리 현상한다. 보정하지 않은 RAW는 현상이 끝날 때까지 파일 안의 카메라 미리보기를 먼저 보여 준다.

## HDR 하이라이트

`EditSettings.hdrAmount`(0…2, 0이면 끔)는 RAW에만 쓴다. 보정 결과(SDR, 선형 작업 공간)를 그대로 두고, RAW를 `CIRAWFilter.extendedDynamicRangeAmount`로 한 번 더 현상해 보통 현상과의 밝기 비율(1…16)을 구한 뒤 같은 구도(회전·크롭·크기)로 옮겨 곱한다. 톤·색·부분 보정·LUT는 SDR 결과를 따르고 SDR 흰색을 넘는 부분만 밝아진다. Core Image의 나누기·곱하기 혼합 필터는 결과를 0…1로 잘라 직접 만든 Metal 커널을 쓴다. 편집 미리보기는 HDR을 표시할 수 있는 화면이 있을 때만 확장 범위(Display P3 선형, 16비트 부동소수)로 그리고, 슬라이더를 끄는 동안의 근사는 SDR이다. 썸네일·히스토그램은 SDR이다. 내보내기는 SDR 결과(워터마크 포함)를 기본 이미지로, 배율을 곱한 이미지로 `kCIImageRepresentationHDRImage` 게인 맵을 만들어 JPEG 또는 HEIF(10비트)로 쓴다. 촬영 정보·키워드는 기본 이미지 속성으로 넣는다. TIFF는 SDR이다. S9 표본은 기본 노출에서 가장 밝은 곳도 SDR 범위 안이라 효과가 거의 없고(1을 넘는 픽셀 2개), +1.5 EV에서는 최대 2.5배(HDR 1)·4.2배(HDR 2)까지 밝아지며 중간 톤 비율은 1.000이었다. 화면에 보이는 HDR은 사람이 확인해야 한다.

## Google Drive 업로드 (2026-09-27)

사용자가 내보내기에서 Google Drive를 고르고 업로드를 실행한 사진만 전송한다. 원본은 파일 바이트를 그대로 보내며, 보정본은 기존 내보내기 파이프라인으로 만든 임시 파일을 보낸다. 같은 원본의 가상 사본을 여럿 골라도 원본은 한 번 보내고 보정본은 각각 보낸다. 임시 결과를 카탈로그의 `lastExport`로 기록하지 않는다. 원본·카탈로그·로컬 내보내기 동작을 유지한다.

`GoogleDriveClient`는 Drive REST API의 계정 확인, Lighthouse에서 만든 폴더 조회·생성, 업로드를 담당한다. `GoogleDriveAuthorization`은 외부 브라우저의 데스크톱 OAuth 로그인과 만료된 토큰 갱신을 담당하며, PKCE·state와 127.0.0.1 loopback callback을 사용한다. 설정과 토큰은 키체인에 저장한다. 요청 범위는 `drive.file`이며 임의의 기존 폴더나 Drive 전체를 탐색하지 않는다. 설정 JSON의 endpoint를 신뢰하지 않고 Google endpoint를 고정한다.

업로드에는 미리 발급받은 파일 ID와 resumable session을 사용하며 원본 전체를 메모리로 읽지 않고 파일에서 전송한다. 서버가 반환한 session 주소의 호스트·경로·HTTPS를 검증하고 리디렉션을 따르지 않는다. 응답을 놓쳤으면 같은 파일 ID를 조회해 ID와 파일 크기가 일치할 때만 완료로 판단하며, 알 수 없는 경우 재시도 전에 Drive에서 확인하도록 안내한다. 취소는 이후 파일 시작을 막지만 이미 서버에 도착한 파일을 삭제하지 않는다. 같은 이름의 기존 원격 파일을 덮어쓰거나 공유 권한을 바꾸지 않는다.

`GoogleDriveUploadModel`은 선택한 계정·폴더·사진·내보내기 설정을 작업 시작 시점에 고정하고, 준비·전송·결과와 취소를 관리한다. 인증과 업로드 작업 중에는 관련 선택 변경을 막는다. 사진 준비는 메인 액터 밖에서 수행하고, 각 편집본의 전송 성공·실패·취소 직후 해당 임시 파일을 정리한다. 배치가 끝날 때까지 파일명을 대소문자 구분 없이 예약하므로 앞 파일을 정리한 뒤에도 다음 편집본의 이름이 중복되지 않는다. 기본 내보내기는 Mac이며 자동 전송·카탈로그 동기화는 하지 않는다. 설정과 사용 범위는 [Google Drive 안내](google-drive.md)에 적는다.

## XMP 사이드카

`XMPSidecar`는 켠 경우에만 원본 옆 `<이름>.xmp`에 `xmp:CreatorTool="Lighthouse"`, `xmp:Rating`(제외는 -1), `xmp:Label`, `dc:subject`, `dc:description`을 쓴다. 파일이 없거나 Lighthouse가 쓴 모양 그대로인 파일(다시 읽은 값으로 만든 문서와 바이트 단위로 같음)만 쓰고, 내용이 같으면 다시 쓰지 않는다. 카메라·다른 앱이 만든 파일과, 이 표시가 남아 있어도 다른 앱이 항목을 더하거나 고쳐 저장한 파일은 건드리지 않는다. `<이름>.xmp` 사이드카는 RAW의 방식이라(Lightroom 등은 JPEG·HEIC에서 파일 안의 XMP를 읽는다) RAW에만 쓰고 가상 사본은 쓰지 않는다. 사이드카가 없는 사진은 적을 표시(별점·제외·라벨·키워드·설명)가 생길 때 만들고, 이미 쓴 사이드카는 표시를 모두 지워도 별점 0으로 고쳐 쓴다. 표시를 바꾸면 0.4초 모았다가 백그라운드에서 쓴다. 종료할 때는 카탈로그·폴더를 저장한 뒤, 대기 중이거나 실패했던 사이드카의 최신 표시까지 저장한다. 실제 쓰기 실패가 남으면 종료를 취소하고 알리며, 외부 사이드카를 보존해 건너뛴 것은 실패로 보지 않는다. 사이드카 기능을 끄면 새 쓰기를 중단하고 이미 큐에 들어간 작업만 마친다. 원본 파일과 보정값은 쓰지 않는다.

## 다시 내보내기

내보낼 때마다 `PhotoAsset.lastExport`(`ExportRecord`)에 시각·파일 경로·번호 접미사 전 이름·설정·보정 요약·파일 크기·수정 시각·파일 전체 SHA-256을 남긴다. 보정 요약은 보정·키워드·설명을 정렬된 JSON(자동 마스크는 내용 해시)으로 적어 SHA-256 앞 16바이트로 줄인 것이며 별점·라벨·스냅숏은 파일에 들어가지 않아 뺀다. 요약이 달라진 사진만 다시 내보내며 그때의 설정·폴더·이름을 쓴다. 사진마다 마지막 기록 하나만 남긴다. 파일 해시가 없는 예전 기록도 읽을 수 있지만 이전 파일을 교체하는 근거로 사용하지 않는다.

다시 내보낼 때는 먼저 아직 쓰이지 않은 파일명으로 새 결과를 완전히 쓴다. 쓰기가 실패하면 이전 파일은 그대로 남는다. 새 결과가 준비된 뒤에만 이전 파일의 크기·수정 시각·SHA-256과 현재 카탈로그의 원본 참조를 확인한다. 모두 안전하고 가져오기도 진행 중이 아닐 때 휴지통으로 옮긴다. 이 판단과 이동은 메인 액터에서 함께 수행한다. 이동에 실패하면 이전 파일과 새 결과를 모두 보존하고 새 결과를 기록하며 정리 실패를 알린다. 이동에 성공하면 기존 기본 이름으로 `renamex_np(RENAME_EXCL)`를 시도하되 다른 파일을 덮어쓰지 않는다. 원본으로 참조 중인 이름이거나 이름 변경에 실패하면 새 결과의 번호 붙은 이름을 유지한다.

로컬 내보내기나 Google Drive 작업 중 종료를 요청하면 취소 여부를 확인한다. 종료를 선택하면 두 작업에 즉시 취소를 전달하고 현재 파일 처리와 정리가 끝나기를 비동기로 기다린다. 로컬 내보내기의 완료 기록을 반영한 뒤 카탈로그·폴더·XMP를 저장하고 종료하며, 저장에 실패하면 앱을 유지한다.

카드 복사는 같은 이름·크기의 기존 파일을 SHA-256으로 비교한 뒤에만 중복으로 건너뛴다. 수정 시각이 같아도 내용이 다르면 번호를 붙여 별도로 복사한다. 내보내기의 IPTC 키워드·설명은 현재 카탈로그 값을 따르며, 비어 있으면 원본의 해당 항목도 결과에서 제거한다. 다른 IPTC 항목과 촬영 정보의 기존 보존 규칙은 유지한다.

## 자동 보정

`AutoAdjust`는 구도와 RAW 현상 설정만 남긴 상태를 192px로 실제 현상해 재고, 색온도·틴트·노출·하이라이트·섀도만 바꾼다. 화이트밸런스는 채도가 낮은 30% 가운데 밝은 절반(주 조명을 받는 흰 면)의 픽셀을 처음 한 번 골라, 그 픽셀의 파랑−빨강, 초록−(빨강·파랑 평균) 차이가 0이 되는 색온도(±1500K)·틴트(±40)를 할선법으로 찾는다. 어두운 사진은 로그 평균 밝기를 18% 회색에 맞추되 가장 밝은 0.5%가 잘리지 않는 만큼만 노출을 올린다. 밝은 사진은 흰 피사체 때문에 전체가 어두워지지 않도록 95번째 백분위 밝기를 선형 0.90까지 내리는 범위로 노출 감소를 제한한다. 해당 밝기가 이미 0.90 이하면 노출을 내리지 않으며, SDR 측정에서 최대 감소는 약 0.15 EV다.

제안 노출을 반영했을 때 잘리는·뭉개지는 비율로 하이라이트(0.6/0.8/1)·섀도(0/0.15/0.3)를 정한다. 이미 밝은 사진의 변화가 작을 수 있다. 밝기 증가 자체를 품질 향상으로 취급하지 않으며, 원본의 대비와 색을 유지하는지를 함께 판단한다. 얼굴 검출값으로 전역 섀도를 크게 올리는 시안은 실제 사용자 평가에서 원본보다 나빠져 철회했다. 현재 자동 보정에는 얼굴 기반 강제 밝기 상승이나 감성 필터를 넣지 않는다. 편집 미리보기의 빠른 근사는 S9에서 색이 실제보다 1.5–2배 움직여 쓰지 않는다.


## 이미지 처리 계약

- RAW 파일은 `CIRAWFilter(imageURL:)`를 사용한다. 내장 JPEG를 최종 보정 원본으로 사용하지 않는다.
- 원본의 RAW 중립 색온도·틴트를 기준으로 상대 화이트밸런스 조절값을 적용한다. 기본값에서 촬영 시 화이트밸런스를 보존한다.
- JPEG·PNG 등 RAW가 아닌 사진도 색온도 +는 따뜻하게, 틴트 +는 마젠타로 RAW와 같은 방향이다(2026-09-25 수정 전에는 반대였다). 같은 값의 세기는 RAW와 다를 수 있다.
- 빠른 썸네일은 Image I/O를 사용할 수 있다. 편집 미리보기는 RAW 현상 후 화면 크기로 축소하고, 100% 보기는 원본 해상도로 요청한다.
- 화면용 렌더(편집 미리보기·다음 사진 미리 현상·보정 썸네일·크롭 창·비교 기준)는 RAW를 출력에 필요한 비율의 1.6배 이상인 2^(-k/4) 배율로 줄여서 현상한다(S9 2200px에서 0.59배). 배율을 정할 원본 크기는 RAW 디코더를 만들지 않고 파일 속성(픽셀 크기·방향)으로 읽는다. 선명도 반경도 같은 비율로 줄인다. 원본 해상도로 현상해 줄인 결과와 픽셀이 같지는 않다(S9 평균 차이 약 1.5/255, 잔 디테일 약 20% 적음). 내보내기·JPEG 압축 미리보기·참조 색감 분석·100% 보기는 원본 해상도로 현상한다. 일반 사진과 필름 입자가 있는 사진은 줄이지 않는다(입자는 해상도에 따라 보이는 세기가 불규칙하게 달라진다). 스팟 복구 패치 탐색은 256px 분석이라 같은 배율의 현상 결과를 쓴다.
- 최종 출력은 전체 해상도의 같은 보정 파이프라인을 사용하고 sRGB JPEG로 인코딩한다. 출력 시 필요하면 지정 긴 변으로 축소한다.
- `CIContext`를 재사용하고, 변경 가능한 `CIFilter` 인스턴스를 작업 사이에 공유하지 않는다. 색 관리를 유지한다.
- 90도 회전·수평 보정 후 안전 캔버스 안에서 자유 크롭을 적용한다. 이전 중앙 비율 크롭도 호환한다. 이미지와 마스크·복제 브러시가 공통 좌표 변환을 사용한다.
- 출력 파일명 충돌은 `-2`, `-3` 등의 접미사로 회피하며 원본 경로와 기존 파일을 덮어쓰지 않는다.

## 화면

어두운 중성 회색 작업 공간. 왼쪽 라이브러리·폴더·선별 필터, 가운데 그리드/큰 사진/비교, 오른쪽 보정·메타데이터 패널(빛·색상이 먼저), 사진·비교·여러 장 보기의 아래 필름스트립(그리드에는 없음). 창이 좁으면 위쪽 도구가 아이콘 메뉴로 접힌다. 한국어 UI를 기본으로 한다. 처음에는 가져오기 버튼과 지원 포맷 안내를 제공하며 빈 상태에 가짜 사진·수치를 넣지 않는다.

## 역할

Astra가 설계, 파일별 구현 계약, 최종 통합·이미지·UI 검증을 맡는다. Sol은 확정된 계약에 따라 코어와 앱 구현을 서로 다른 파일 범위에서 담당한다. 새로운 설계 판단은 Astra에게 반환한다.

## 전체 점검 뒤 개선 (2026-09-25)

- 부분 보정 마스크는 출력 긴 변에 필요한 해상도로만 그린 뒤 이미지 크기로 늘린다. 편집 미리보기 파이프라인은 모양이 같은 마스크를 최근 8개까지 기억하므로 효과 값만 바꾸는 동안 다시 그리지 않는다. 원본 해상도 출력은 이전과 같다.
- 마스크 표시는 모양·구도가 그대로면 건너뛰고, 그리는 중에 들어온 요청은 마지막 것만 남긴다.
- 슬라이더를 끄는 동안 RAW 노출·색온도·틴트가 바뀌면 최근 현상 결과에 차이를 덧씌워 근사로 그린다(노출은 EV, 색온도는 RAW 중립 색온도 기준의 미레드 차이 ×1.35, 틴트 ×1.4). 끝나거나 0.25초 멈추면 정확히 현상하며, 근사 결과는 썸네일·최근 렌더로 남기지 않는다.
- RAW+JPEG 한 장으로 보기는 같은 목록에 RAW가 있을 때만 JPEG 짝을 숨긴다. 목록과 개수 모두 같은 규칙이다.
- 명료도·입자·복구 보정 커널은 `CIKernel.kernels(withMetalString:)`로 실행 중에 컴파일한다. 빌드에 Metal 도구가 필요 없다.

## 가상 사본 (2026-09-25)

`PhotoAsset.snapshots`(이름·저장 시각·보정)는 비어 있으면 쓰지 않으며, 스냅숏의 자동 마스크도 `Masks`에서 지우지 않는다. 보정 기록은 실행 취소 이력에서 그 사진의 보정 변경만 꺼내 보이며 앱을 다시 열면 사라진다. 기록·스냅숏으로 돌아가기는 새 보정 단계로 남는다. `PhotoAsset.keywords`·`caption`·`colorLabel`은 비어 있으면 카탈로그에 쓰지 않고, 별점·표시와 함께 `PhotoMarks` 한 단위로 실행 취소된다. 내보내기는 IPTC 키워드·설명(Caption-Abstract)으로 넣는다. `PhotoAsset.copyName`이 있으면 같은 `path`를 가리키는 가상 사본이다. 카탈로그 버전은 1을 유지하며 키가 없는 기존 항목은 원래 항목으로 읽는다. 사진을 구분하는 모든 캐시(썸네일·최근 렌더·미리 현상·내보내기 미리보기)는 경로가 아니라 항목 ID로 찾는다. 가져오기 중복 검사는 경로 기준이라 같은 파일을 다시 가져와도 항목이 늘지 않는다. 사본 삭제와 카탈로그에서 빼기는 같은 경로로 카탈로그·내 폴더·메모리 썸네일·연속 촬영 분석에서 그 항목만 지운다. 원본 파일에는 손대지 않는다. 빼기는 실행 취소 한 단계(`HistoryStep.removal`)로 남아 빼기 전 순서·보정·표시·내 폴더 소속과 함께 되돌린다. 그 사진의 앞선 보정·표시 단계도 남겨 되돌린 뒤 이어서 실행 취소할 수 있다. 그사이 같은 파일(같은 사본 이름)을 다시 가져왔으면 그 항목은 되돌리지 않는다. 디스크 썸네일은 되돌릴 때를 위해 두었다가 다음 실행 때 카탈로그에 없는 ID의 폴더를 지운다.

## 연속 촬영 묶음 (2026-09-25)

`BurstGrouping`이 카메라별 촬영 시각(초 미만 포함)으로 1초 이내 컷을 묶고, 같은 폴더·같은 이름 파일은 한 컷으로 본다. `PhotoQualityAnalyzer`는 1024px 원본 미리보기에서 칸별 라플라시안 분산의 상위 10%와 Vision 얼굴 촬영 품질을 구한다. `BurstRanking`은 제곱근으로 정규화한 선명도와 얼굴 품질을 반씩 더해 추천한다. 분석 결과는 카탈로그에 저장하지 않는다. 묶음은 사진 목록의 ID·경로·촬영 시각·카메라 서명이 바뀔 때만 다시 계산한다.

## 사람별 사진 분류 (2026-09-29)

`FaceAnalyzer`는 방향을 적용한 2048px 원본 미리보기에서 Vision 얼굴 특징점을 구하고 다섯 점으로 얼굴을 정렬한다. 앱에 포함한 Apache 2.0 SFace 모델을 Core ML로 실행해 정규화한 128차원 얼굴 특징을 만든다. 모델은 CPU에서 실행하며 실행 중 다운로드하지 않는다. 모델 변환 스크립트·라이선스·출처를 저장소에 함께 보관한다.

`PeopleStore`는 이름·얼굴 미리보기·확인 및 제외 결과를 독립적인 `people.json`에 저장한다. `FaceMatching`은 사용자가 확인한 얼굴과의 코사인 유사도로 후보를 구하며, 후보를 다시 비교 기준으로 사용하거나 자동으로 이름을 확정하지 않는다. 이름 검색과 사람 필터에는 확인한 얼굴만 포함한다. 원본·보정·XMP는 변경하지 않는다. 비동기 분석은 사진 경로와 파일 서명을 확인한 뒤 결과를 반영하며, 중지·종료 시 완료된 결과를 저장한다. 자세한 범위는 [사람별 분류 계약](people-contract.md)과 [사용 안내](people.md)를 따른다.

## 부분 보정 확장 (2026-09-23)

사용자 요청으로 브러시·지우개 마스크와 영역별 노출·대비를 추가했다. `EditSettings.localAdjustments` 배열에 원본 기준 정규화 좌표의 스트로크를 저장한다. 이 키가 없는 기존 카탈로그는 빈 영역 배열로 읽고, 잘못된 타입이나 명시적인 null은 손상으로 처리한다.

전체 보정 뒤, 회전·크롭 전에 영역 효과를 선형 회색 마스크로 순서대로 합성한다. EXIF 방향 적용 후 원본 좌상단 좌표를 기준으로 하므로 사용자 회전·크롭 변경에도 같은 피사체에 적용된다. UI에서 칠하기는 화면 맞춤 상태로 제공하며, 최종 JPEG는 원본 해상도 마스크를 사용한다. 자세한 인터페이스와 검증 조건은 [부분 보정 계약](local-adjustments-contract.md)을 따른다.

## LUT 확장 (2026-09-23)

`EditSettings.lut`는 보관 파일의 내용 해시, 이름, 활성화 여부와 강도를 저장한다. 기존 카탈로그의 키 누락은 LUT 없음으로 복원한다. `LUTStore`는 검증한 3D `.cube`를 카탈로그 옆 `LUTs` 폴더에 보관하고 무결성을 검사한다. 카탈로그에 색상 표 전체를 중복 저장하지 않는다.

전체·부분 보정 뒤에 sRGB로 색을 변환하고 도메인 정규화와 3D 색상표 조회를 수행한 다음 Core Image 작업 공간으로 복귀한다. 강도는 LUT 전후 이미지를 작업 공간에서 합성하는 비율이다. 미리보기와 JPEG는 같은 경로를 쓰며, 원본 보기와 LUT 강도 0/비활성화는 효과를 우회한다. LUT 읽기·파싱은 UI 스레드 밖에서 처리하며 선택이 바뀐 사진에 늦게 적용하지 않는다. 범위와 인터페이스는 [LUT 계약](lut-contract.md)을 따른다.

## 보관·일괄 편집·참조 색감·폴더 확장 (2026-09-23)

- LUT 파일 옆 이름 sidecar를 보관하고 전체 목록을 조회한다. 이전 sidecar 없는 파일도 읽으며 개별 손상을 목록 오류로 격리한다. 여러 `.cube`를 한 번에 추가할 수 있다.
- `PhotoSelectionState`는 선택 집합·기준·범위 시작점을 관리한다. `EditComponents`로 보정 범위를 명시하고 `EditHistory`로 여러 사진 변경을 한 실행 취소 단위로 저장한다. 보이지 않는 사진을 대상에서 제외한다.
- `ReferenceColorMatcher`는 현재 사진의 LUT를 제외한 sRGB 렌더와 참조의 색 통계를 분석한다. CIELAB 평균·표준편차의 제한된 변환을 33³ 색상표로 만든다. 사진의 공간적 내용은 바꾸지 않는다. 생성 강도는 sRGB 변환 안에 저장하며, 이후 앱의 LUT 강도 슬라이더는 기존 선형 작업 공간 혼합을 사용한다.
- S9용 생성 파일은 full range 및 `#LUMIXPHOTOSTYLE STD`로 Standard 기반을 명시한다. V-Log 변환은 제공하지 않으며 실기 로딩·촬영은 별도 검증 대상이다.
- `PhotoFolderStore`는 `folders.json`에 폴더 이름과 사진 ID 집합을 저장한다. 실제 파일 경로와 보정 카탈로그를 변경하지 않는다. 폴더 로드 오류가 있어도 사진 보정은 계속할 수 있고, 손상된 폴더 파일은 덮어쓰지 않는다.

각 확장 계약과 사용자 안내는 README에 연결한다. 네 가지 기능도 원본 파일을 참조만 하고 결과를 별도로 저장한다.

## 고급 보정 확장 (2026-09-23)

승인한 여섯 기능의 저장·처리·화면 경계는 [고급 보정 계약](advanced-editing-contract.md)에 정의한다.

- Vision이 생성한 원본 방향의 회색 마스크를 카탈로그에 저장한다. 피사체/반전 배경 위에 수동 브러시를 더하고 지운다.
- RGB 곡선과 HSL 색상 범위는 sRGB 수치의 Float 색상표를 통해 처리한다. 필름 입자는 저장된 seed와 원본 픽셀 좌표로 재현한다.
- `PhotoGeometry`가 quarter turn·수평 안전 영역·정규화 자유 크롭의 좌표를 일원화한다. 기존 부분 보정과 복구 위치는 원본 좌표로 보존한다.
- 복제와 주변 패치 스팟 복구는 별도 stroke 배열에 저장한다. 복구는 작은 결함의 질감·밝기를 완화하는 방식이며 생성형 제거는 아니다.
- 전체 처리 순서는 현상 → 노이즈 감소 → 전체 보정 → 복구 → 곡선/HSL → 부분 보정 → LUT → 입자 → 구도 → 출력 축소다. 원본 보기에서는 중립 설정을 사용한다.
- JPEG 미리보기는 실제 압축 데이터를 디코딩해 보여준다. 내보내기 시 사진·보정·출력 옵션이 정확히 같은 경우 준비된 데이터를 재사용한다.

사용 방법은 [고급 보정 안내](advanced-editing.md), 실제 검사 결과와 남은 범위는 [검증 기록](verification.md)을 따른다.

## JPEG·HEIC 및 AI 노이즈 감소 (2026-09-29)

`EditSettings.noiseReduction`에 끔·일반·AI와 강도를 저장한다. 이전 카탈로그는 끔으로 읽고, 전체 보정 복사·일괄 적용·실행 취소·스냅샷에 같은 값을 사용한다. 일반 방식은 Core Image, AI는 번들에 포함한 MIT 라이선스 FFDNet 모델을 Core ML로 실행한다. 사진과 모델 추론은 Mac 안에 머문다.

AI는 방향을 적용한 원본 해상도의 RGB 이미지를 겹치는 타일로 처리한다. 투명도와 범위 밖 하이라이트 잔차를 보존하고 결과 한 장을 재사용한다. RAW 노출·화이트밸런스·현상 옵션은 캐시를 갱신하지만 이후 대비·LUT·출력 크기는 다시 추론하지 않는다. 모델 누락이나 추론 실패는 오류로 표시한다. 사용자 안내는 [노이즈 감소](denoise.md), 저장·색·타일·번들 경계는 [구현 계약](denoise-contract.md)을 따른다.

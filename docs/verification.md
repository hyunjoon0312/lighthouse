- **원본 없는 사진의 썸네일**: 보정 여부와 관계없이 사진마다 최신 썸네일을 `Thumbnails`에 두고, 원본을 읽을 수 없으면 마지막 썸네일을 보여 준다. 보관한 썸네일도 없는 사진은 원본이 돌아올 때까지 다시 찾지 않는다. 다시 연결하면 새로 만든다. 모델 흐름 검사에서 대체 썸네일을 끄면 "fallback thumbnails"에서 시간 초과로 실패하는 것을 확인했다. release 앱에서는 보정하지 않은 2장의 썸네일이 저장되는 것과, 원본 폴더를 옮긴 뒤 다시 실행해도 "missing originals: 2 of 2"를 기록하며 정상 동작하는 것을 확인했다.
- **F 연타**: 전체 화면 전환 중의 요청은 AppKit이 무시하므로 미뤘다가 전환이 끝나면 마지막 상태로 맞춘다. 판단 규칙을 `FocusFullScreen`으로 빼서 두 번·세 번 누르기, 나가는 중 다시 누르기, 초록 버튼 종료, 원래 전체 화면인 창을 단위 테스트로 확인했다. 실제 창의 전환 애니메이션은 확인하지 못했다.
- **보관본 마스크**: 보관본에 `Masks` 폴더를 두고 원래 마스크 파일을 하드 링크한다(같은 inode임을 테스트로 확인). 원래 파일이 망가졌거나 없으면 메모리의 마스크로 쓴다. 원래 마스크를 지워도 보관본의 `catalog.json`과 `Masks`만으로 열린다. 이전 보관본(마스크가 카탈로그 안에 있는 형식)도 그대로 읽힌다.
- **RAW 원본 크기**: 줄여 현상할 배율을 정할 때 CIRAWFilter 대신 ImageIO 속성(픽셀 크기·방향)을 읽는다. S9 한 장에 약 28ms → 2ms(두 번째 호출부터, 첫 호출은 프레임워크 적재로 둘 다 느림). S9 원본과 방향 태그만 6으로 바꾼 복사본 모두 디코더 결과(6000×4000, 4000×6000)와 같다.
- **시간 비교 검사**: 모델 흐름 검사의 시간 비율 단언 두 곳을 없앴다. 다시 실행한 뒤 보관한 썸네일 파일이 다시 쓰이지 않았는지(수정 시각·파일 하나), 목록 읽기 캐시가 채워지고 사진이 바뀌면 비워지는지로 확인한다. 걸린 시간은 출력만 한다.
- **화면 확인**: 한 번 더 시도했지만 `screencapture` 결과가 전부 검은색(밝기 0)이고, Orca는 권한이 "granted"로 나오는데도 `permission_denied`(접근성 읽기 차단)를 돌려준다. Orca는 시스템 설정에서 Orca Computer Use의 손쉬운 사용 권한을 껐다 켜라고 안내한다.

## 추가 기능 검토 뒤 수정 6개 — 2026-09-27

14개 기능을 다시 읽고 찾은 결함 3개와 개선 3개를 고쳤다(`0bffc91`…`e2e8114`). 고친 동작마다 회귀 테스트를 넣었고, 결함 3개의 테스트는 이전 코드에서 실패하는 것을 확인했다.

- **다시 내보내기**: "이전 파일은 휴지통으로"를 켜면 새 파일을 만들기 전에 이전 파일을 옮겨, 원본이 없으면 이전 파일만 휴지통으로 가고 새 파일은 없었다. 이제 새 파일 데이터를 먼저 만든다. 원본이 없는 사진은 다시 내보낼 목록에서 뺀다.
- **HDR과 복제·스팟 복구**: HDR 배율을 복구 전 RAW에서 구해, 복구로 가린 밝은 물체의 배율이 그대로 남았다. S9에서 가장 밝은 곳을 어두운 곳으로 덮으면 화면 값은 0.028인데 HDR에서 1.78배가 곱해졌다. 이제 복구가 쓴 원본 위치에서 배율을 옮겨 온다. 스팟 복구의 밝기 맞춤은 0…1로 잘라 배율에 쓸 수 없으므로 배율은 복제처럼 옮긴다. 덮은 곳의 배율은 1.1배 미만이고, 밝은 곳을 복제해 온 자리는 1.4배를 넘는다(이전 코드 1.0배).
- **XMP 사이드카 소유 판단**: `CreatorTool="Lighthouse"` 글자만 보고 덮어써서, 다른 앱이 이 표시를 남긴 채 더한 보정값(`crs:` 등)을 지웠다. 이제 Lighthouse가 쓰는 값만 다시 읽어 만든 문서와 바이트 단위로 같을 때만 덮어쓴다. Lightroom이 실제로 이 표시를 남기는지는 확인하지 않았다.
- **XMP 사이드카 대상**: RAW에만 쓰고, 적을 표시(별점·제외·라벨·키워드·설명)가 생긴 사진에만 새로 만든다. 이미 쓴 사이드카는 표시를 모두 지우면 별점 0으로 고친다. Lightroom 등이 JPEG·HEIC의 사이드카를 읽지 않는다는 판단은 이번에 확인하지 않았다.
- **초점거리 보충**: 원본에 초점거리가 없는 사진을 실행마다 다시 읽었다(가져오기·내보내기와 같은 큐, S9 한 장 약 1.8ms). 이제 없음을 기록해 한 번만 읽는다. release 앱에서 예전 형식 카탈로그로 두 번 실행해 첫 실행에만 "checked focal length of 1 photos, found 1"이 기록되는 것을 확인했다.
- **사진 끌기 형식**: 끌 때 일반 텍스트를 넘겨 Finder나 메모에 놓으면 텍스트 클리핑이 생겼다. 이제 Info.plist에 선언한 앱 전용 형식(`com.rian.lighthouse.photos`)만 이 프로세스에 보이게 넘긴다. 등록된 형식이 이것 하나이고 되읽을 수 있음을 테스트로 확인했지만, 다른 앱에 놓았을 때의 동작은 화면에서 확인하지 못했다([화면 수동 점검표](manual-qa.md)).
- `swift test` **154개, 실패 0개**(S9 RAW·얼굴 표본 포함). 처음부터 다시 한 debug 빌드 경고 0개. `./scripts/build-app.sh`, `codesign --verify --deep --strict dist/Lighthouse.app` 통과. 격리 카탈로그로 release 앱을 세 번 실행(S9 사본 가져오기 포함)한 뒤 각 PID만 종료했고 크래시 보고서는 없었다. S9 원본 SHA-256은 기존 값과 같다.

## 화면 점검으로 찾은 UX 개선 — 2026-09-27

화면 캡처와 Orca 접근성 읽기는 여전히 막혀 있어, SwiftUI 화면을 창 밖에서 PNG로 그려 보며 점검했다(`UISnapshotTests`, `LIGHTHOUSE_SNAPSHOT_DIR`을 줄 때만 동작). 이 방법으로 찾은 결함과 개선을 기능마다 커밋했다(`9a9b48f`…`1950f49`). 클릭·키 입력·핀치·HDR 밝기는 이 방법으로 확인할 수 없어 [화면 수동 점검표](manual-qa.md)에 넣었다.

- **그리드 선택·제외 표시가 보이지 않음**: 표시 아이콘이 다중 선택 동그라미 바로 밑에 그려져 가려졌다. 별점 줄로 옮기고 제외한 사진은 흐리게 했다. 선택 표시는 다중 선택 체크와 헷갈리지 않게 모든 곳에서 깃발 아이콘으로 바꿨고, 필름 스트립에서 "기준" 글자에 가려지던 표시는 왼쪽 위로 옮겼다.
- **일괄 적용 창의 대상 목록이 비어 보임**: 내용 크기에 맞춰진 창 안의 스크롤 영역이 0 높이가 됐다. 줄 수만큼 높이를 준다.
- **좁은 창(1100×720)**: 위쪽 제목·장수가 사라지고 선택 줄의 "폴더에 추가"가 잘렸다. 비교 보기 머리줄 단추는 두 줄로 꺾였다. 제목은 보고 있는 목록 이름이 되고, 좁으면 별점·정렬은 아이콘 메뉴로, 두 확인란은 "보기" 메뉴로 접힌다. 머리줄 단추는 한 줄을 유지하고 이름이 먼저 줄어든다. 그리드에는 같은 사진을 반복하던 필름 스트립을 두지 않는다.
- **여러 장 표시**: 그리드에서 여러 장을 골라도 별점·표시·라벨이 기준 사진 한 장에만 붙었다. 이제 고른 사진 모두에 한 번의 실행 취소 단계로 붙는다(사진 보기에서는 한 장).

## 자동 보정의 밝은 장면 노출 감소 수정 — 2026-10-01

사용자가 실제 앱에서 ⌘?를 누르자 도움말 대신 단축키 창이 열렸다. - 새 `HelpGuideTests.testCommandQuestionMarkIsTheHelpKey`(⌘⇧/만 도움말, ?는 단축키, ⌘/는 메뉴)와 `testKeyMonitorOpensHelpForCommandQuestionMark`(실제 `WorkspaceView`의 키 감시에 `NSApp.sendEvent`로 ⌘⇧/를 보내 도움말이 열리고 단축키 창은 열리지 않음). 앞 테스트는 함수가 없어 컴파일 실패로, 뒤 테스트는 고친 줄을 잠시 끈 상태에서 실패하는 것을 본 뒤 통과했다. 처음에는 이벤트를 `nextEvent`로 꺼내 시험했는데 키 감시는 `sendEvent`에서만 불려 고친 뒤에도 실패해, 이 테스트가 감시를 지나지 않는다는 것을 알고 바꿨다.
- 최종 트리: 전체 `swift test`(얼굴 표본 포함) 454개. 첫 실행에서 `HDRFlowTests.testPreviewIsHDROnCapableScreenAndThumbnailStaysSDR`가 썸네일 대기 60초 시간 초과로 실패했다(이전 점검에서도 한 번 있었던 간헐 실패). 따로 세 번은 모두 1.4초 안팎에 통과했고, 다시 돌린 전체 실행은 실패 0개(11개 건너뜀)였다. 썸네일 경로는 이번 변경과 관계없다. 썸네일 기억(NSCache)이 메모리 압박에 비워진 뒤 다시 요청되지 않는 경우로 보이나 확인하지는 않았다. `swift build -c release` 통과(경고 없음).
- 확인하지 않은 것: 사용자가 Mac을 쓰는 중이라 QA 앱을 앞으로 띄우거나 실제 키를 보내지 않았다(QA 앱을 띄우면 스스로 맨 앞으로 오고, 앞서 확인용으로 한 번 앞으로 올렸다). 창 이벤트 테스트(`UIEventTests`)도 실제 마우스 포인터를 옮겨 이번에는 돌리지 않았다(이번 변경은 키 처리만 건드린다). 실제 앱에서 ⌘?는 사용자 확인이 필요하다.

### 보이는 칸의 썸네일이 지워진 뒤 다시 채워지지 않는 문제 — 2026-10-11

`HDRFlowTests.testPreviewIsHDROnCapableScreenAndThumbnailStaysSDR`의 간헐 실패(썸네일 60초 대기 시간 초과)를 조사했다. 이날 전체 실행 기록 17개 중 2개(11:48, 23:23)에서 같은 테스트만 실패했다. 두 번 모두 가져오기·첫 렌더·HDR 렌더는 2초 남짓에 끝났고 다른 오류 줄은 없었으며, 겹친 테스트 실행도 없었다.

- 임시 진단 테스트로 같은 과정을 한 프로세스에서 20번, 전체 실행 끝에 붙여 20번 되풀이했다. 40번 모두 보정 렌더가 썸네일을 미리 넣어 두어 테스트의 요청은 할 일이 없었고, 캐시가 비워지는 일(NSCache 대리자로 셈)도 없었다. 그 전체 실행 455개도 실패 0개였다. 실패를 재현하지 못해 원인은 확정하지 못했다. 이 테스트는 썸네일을 한 번만 요청하므로, 그 사이 썸네일이 지워지고 다시 만드는 작업이 결과를 내지 못하면 다시 요청하는 쪽이 없다는 것까지만 확인했다. 진단 테스트는 지웠다.
- 그 과정에서 실제 앱의 버그를 확인했다. 그리드·필름 스트립 칸은 처음 나타날 때와 보정값이 바뀔 때만 썸네일을 요청한다. 그래서 메모리가 모자라 시스템이 썸네일 캐시를 비우거나, 앱이 스마트 미리보기를 만들거나 지울 때·원본이 사라지거나 돌아올 때 캐시를 비우면(`invalidateWorkflowRenderCaches`), 보이는 칸이 스크롤해서 다시 나타날 때까지 회색 아이콘으로 남았다. 창 밖에 띄운 `WorkspaceView`에서 두 경우 모두 5초 뒤 0/4장이었다. 칸이 자기 썸네일이 빈 것을 보면 다시 요청하게 했다(`WorkspaceView`의 두 칸에 한 줄씩).
- 새 `ThumbnailRefillTests` 3개: 그리드에서 앱이 비울 때, 그리드에서 시스템이 비울 때, 사진 보기 필름 스트립에서 앱이 비울 때 보이는 4장이 다시 채워진다. 고치기 전과 고친 줄을 잠시 끈 상태에서 셋 다 실패했고, 고친 뒤 세 번 연속 통과했다. 창 밖 화면은 다시 그리는 때가 들쭉날쭉해(처음 칸 배치에 최대 7초) 기다리는 동안 `layoutSubtreeIfNeeded`로 배치를 돌린다.
- 최종 트리: 전체 `swift test` 457개, 실패 0개(14개 건너뜀), `swift build -c release` 통과(경고 없음).
- 확인하지 않은 것: HDR 테스트 간헐 실패의 실제 원인(재현하지 못함). 실제 앱에서 스마트 미리보기를 만든 뒤 그리드가 바로 다시 채워지는 모습(사용자가 Mac을 쓰는 중이라 앱을 띄워 조작하지 않았다).

### 베스트 컷 분석·여러 장 작업을 멈출 때 "중지하는 중…" 표시 — 2026-10-11

베스트 컷 분석과 여러 장에 하는 작업(스마트 미리보기, 중복·유사 사진 찾기, 일괄 보정, 백업·복원 등)은 중지를 누르면 지금 처리 중인 한 장을 끝낸 뒤에 멈춘다. 그동안 작업 목록·단추가 아무 변화 없이 "중지"/"취소"로 남아 눌리지 않은 것처럼 보였다. 가져오기·내보내기·Drive 업로드·얼굴 찾기에는 이미 있던 멈추는 중 표시를 이 둘에도 넣었다. LED 띠 분석과 Lightroom 프리셋 확인은 누르는 즉시 목록에서 빠지므로 바꾸지 않았다.

- 멈추는 중은 따로 값을 두지 않고 "작업이 아직 돌고 있고 그 작업의 중지 플래그가 켜졌다"로 읽는다(`isCancellingBursts`, `isCancellingWorkflow`). 작업마다 새 플래그를 만들므로, 작업을 켜고 끄는 여덟 곳을 고치지 않아도 끝나면 저절로 풀리고 다음 작업에 남지 않는다. 플래그는 화면이 보는 값이 아니어서 중지할 때 화면에 바뀐 것을 알린다.
- 작업 목록, 연속 촬영 막대의 중지 단추("중지하는 중…"), 스마트 미리보기·유사 사진·백업·복원 시트와 일괄 보정 시트의 취소 단추("취소하는 중…")에 쓰고, 멈추는 동안 단추를 끈다.
- 새 `BackgroundActivityTests` 2개: 베스트 컷 분석을 멈추면 목록에 멈추는 중으로 보인다. 작업 큐를 붙잡아 둔 스마트 미리보기 만들기를 목록에서 멈추면 멈추는 중으로 보이고, 끝나면 풀리며, 다음 작업(유사 사진 찾기)은 멈추지 않은 상태로 시작한다. 목록에 연결하기 전 둘 다 실패했고, 연결한 뒤 `BackgroundActivityTests`·`BurstAnalysisFlowTests`를 세 번 연속 통과했다.
- 최종 트리: 전체 `swift test` 459개 중 14개 건너뜀, 실패는 `HDRFlowTests.testPreviewIsHDROnCapableScreenAndThumbnailStaysSDR` 하나(썸네일 60초 대기 시간 초과, 바로 위 항목의 간헐 실패와 같은 모습)였다. 이 테스트는 썸네일 경로만 보고 이번 변경(중지 표시)과 닿지 않으며, 따로 세 번 돌려 모두 통과했다(4.5~6.2초). 이번에도 원인은 확정하지 못했다. `swift build -c release` 통과(경고 없음).
- 확인하지 않은 것: 실제 앱에서 중지를 눌렀을 때의 모습(사용자가 Mac을 쓰는 중이라 앱을 띄워 조작하지 않았다).

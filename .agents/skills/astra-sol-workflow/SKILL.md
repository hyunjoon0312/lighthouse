# Astra · Sol 작업 계약

## 모델과 권한

- `gpt-6-astra`: 모든 오케스트레이션, 브레인스토밍, 계획·아키텍처·구현 설계,
  복잡하거나 중요한 분석·검토·검증. 판단이 핵심인 스킬·정책 문서는 Astra가 직접 쓴다.
- `gpt-5.6-sol`: 결정된 계약에 따른 단순 코드 작성·일반 수정·정형 실행.
  코딩 중 새 설계 선택이 필요하면 그 부분을 Astra에 돌려 결정을 받아 반영한다.
- 명시적 작업별 모델·effort가 우선한다. 블로그 본문 Astra high, 제목 추천 Sol medium
  같은 설정을 일괄 덮지 않는다. Claude 역할 파일의 `model:`은 Codex 배정이 아니다.
- 모델 선택이 애매하거나 지정 모델이 없으면 그 단계의 대체 전에 사용자에게 묻는다.
  현재 모델에 맞는 독립 작업은 계속할 수 있다. 실제 실행 정보 없이 전환했다고 말하지 않는다.
- 이 문서는 실행 설정이 아니다. 앱의 고정 매핑·구독 CLI·인증·과금 경로를 바꾸지 않는다.
  위임은 사용자 권한을 넓히지 않는다. 발행·메시지·운영 데이터 변경은 원래 승인 범위를 따른다.

## 최소 실행 경로

1. Astra가 결과·비목표·위험·검증 기준을 정한다. 필요한 파일만 읽고 이미 정해진 조건은 재질문하지 않는다.
2. 현재 모델에 맞는 단일 작업이면 직접 처리한다. Astra가 판단 문서를 작성한 뒤 Sol에게
   그대로 다시 쓰게 하거나, 오케스트레이션 스킬을 썼다는 이유만으로 에이전트를 만들지 않는다.
3. 구현 위임이 필요하면 아래 계약을 준다. Astra가 유용한 설계·검토를 병행할 수 있는
   범위부터 나눈다. 추가 작업자는 독립 산출물·겹치지 않는 편집 범위가 있을 때만 쓴다.
4. Sol은 현재 코드를 확인해 범위 안에서 구현하고 관련 검사를 수행한다. 작업 재분해·재위임은 하지 않는다.
5. Astra가 실제 diff·사용자 요구·실행 증거로 중요한 최종 판정을 한다. 기본적으로 조율자가
   이 검토까지 맡으며, 별도 검증자는 실제 독립성이 필요한 위험이 있을 때 추가한다.

effort의 운영 시작점은 Astra 일반 조율 medium / 중요한 설계·검증 high,
Sol 기계적 수정 low / 일반 구현 medium이다. 성능 실측값이나 런타임 기본값이 아니며,
명시된 설정과 현재 도구 지원을 먼저 따른다. 부모의 높은 effort를 모든 작업자에게 복제하지 않는다.

## 위임 계약 — 필요한 항목만 채운다

```text
작업 ID / 계약 버전:
목표와 관찰 가능한 완료 조건:
수정 허용 경로 / 제외 경로 / 기존 변경 보존:
필수로 읽을 파일:
확정된 설계와 인터페이스 (입력·출력·오류·호출 순서):
의존 산출물 / 없어도 먼저 할 수 있는 작업:
검증 명령과 담당자 (작업자 범위 / 통합 검증 범위):
권한 경계 (운영 변경·외부 발행 등):
완료 보고: 변경 파일, 실제 명령·결과, 미실행·남은 결정
```

완성 코드를 계획서에 전부 적어 재입력시키지 않는다. Sol이 구현할 수 있을 만큼의 계약과
관련 예시만 준다. 코드·줄 번호는 현재 파일로 확인하고, 계약 변경은 Astra가 새 버전으로 전달한다.

## 메시지·공유 파일·의존성

- 실제 조율 도구의 현재 문서를 따른다. Orca 조율이면 해당 `orchestration` 스킬을 읽는다.
  존재하지 않는 명령을 추측하지 않는다. 사용 가능한 도구의 권한·위임 제한이 우선한다.
- 작업자는 첫 편집 전, 단계 전환, 완료 보고 전에 새 메시지의 **본문까지** 확인한다.
  제목만 확인한 것을 수신 완료로 보지 않는다. 계약을 바꾸는 메시지는 버전과 적용 범위를 회신한다.
- 기존 작업자를 재사용할 때도 새 계약을 보낸다. 이전 작업의 완료 통보를 새 작업 완료로 오인하지 않는다.
- 같은 파일은 한 명이 소유한다. 실행 중 import되는 파일을 먼저 삭제하고 나중에 생성하지 않는다.
  기존 파일은 Update 패치로 수정하고 새 의존 파일은 호출 코드보다 먼저 만든다.
- 의존 모듈이 아직 없으면 자체 단위 검증과 인계를 먼저 끝낸다. 통합 검증은 의존성이 준비된 뒤
  Astra가 조율한다. 의존 대기 때문에 모든 작업자가 같은 전체 테스트를 반복하지 않는다.
- 도구의 완료 알림·대기 기능을 사용한다. 짧은 반복 폴링·로그 tail을 피한다.
  체크포인트나 예상 시간 초과만으로 정상 실행을 실패로 판정하거나 종료하지 않는다.
- 기존 사용자 변경과 운영 프로세스를 보존한다. 문서 수정만으로 서버 재시작·배포를 하지 않는다.

## 검증과 보고

- Sol: 변경에 직접 관련된 재현·단위 검사. 실패 원인과 실제 출력 요약을 남긴다.
- Astra: 핵심 계약·경계 사례·통합 위험을 독립적으로 확인한다. 구현자의 자기평가를 증거로 쓰지 않는다.
- 전체 스위트는 통합 위험이 있을 때 실행한다. 통과 후 새 변경·실패·미해결 위험 없이 반복하지 않는다.
  문서 변경은 구조·링크·충돌·기존 문서 테스트로 검증한다. 거짓 실패를 만들거나 앱 전체 테스트를 강제하지 않는다.
- HTTP 성공이나 문자열 테스트를 시각적 UI 검증으로 보고하지 않는다. 지침 검사를 실제 모델 성능 측정으로 표현하지 않는다.
- 진행 보고에는 완료한 산출물·확인된 문제·다음 검증을 짧게 쓴다. 근거 없는 완료 시간이나 반복적인 안심 문구를 피한다.
- 최종 보고는 결과, 실제 검증, 남은 한계를 구분한다. 구현 완료·검증 완료·운영 적용 완료를 혼동하지 않는다.
  실제 사용 모델은 확인 가능한 경우만 적는다. 로그 전문 대신 명령·결과와 필요한 실패 구간만 전달한다.

## 유지보수

저장소 안의 `.agents/skills/astra-sol-workflow/SKILL.md`가 해당 프로젝트의 실행 정본이다.
개인 설치본과 저장소 배포본이 함께 있으면 루트 AGENTS.md가 연결한 저장소 파일을 읽는다.
새 프로젝트에도 스킬 폴더의 실제 파일과 공통 규칙을 포함하고, 루트에서 상대 경로로 연결한다.
개인 홈·다른 저장소·옵시디언 볼트가 있어야만 지침을 읽을 수 있는 구조를 만들지 않는다.
공통 배포본 갱신 시 대상 레포의 차이를 먼저 검토하고 같은 버전만 동기화한다.
도메인별 예외는 프로젝트 지침에 두며, 제공업체 캐시 스킬은 복제·일괄 수정하지 않는다.
새 세션에서 지침·스킬이 인식되는지 확인한다. 실행 중인 작업자에게는 바뀐 계약을 별도로 전달해야 한다.

설계 근거: [Astra prompting](https://developers.openai.com/api/docs/guides/latest-model)의 지침 충돌·검증 범위,
[Sol prompting](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.6)의 간결한 작업 계약을 반영했다.
모델 분담 자체는 사용자의 2026-09-08 지시다.

# Lighthouse 개발 팀

## 시작과 완료 조건

사용자의 요청, 현재 diff, 관련 구현·문서·테스트와 기존 실행을 확인한다. 이 스킬은 사진 앱 개발 절차이며 앱에 LLM 서비스나 모델 선택 기능을 추가하지 않는다.

1. 프로젝트 루트 `AGENTS.md`와 [Astra–Sol 계약](../astra-sol-workflow/SKILL.md)을 읽는다.
2. 배정 전 [팀과 파일 경계](references/team.md)를, 변경의 필수 검사를 고를 때 [검증 기준](references/verification.md)을 읽는다. 제품 범위는 루트 `docs/architecture.md`와 해당 기능의 계약 문서를 따른다.
3. 메인 Astra가 사용자에게 보이는 결과, 현재 동작, 변경 계약, 파일별 소유자, 의존 순서, 실제 완료 기준을 확정한다. 기존에 허용된 작업을 다시 승인받지 않는다. 모델 선택이 애매하거나 지정 모델이 가용하지 않은 경우에만 대체 전에 사용자에게 묻는다.
4. 확정된 구현은 Sol에, 복잡한 판단과 중요한 검증은 Astra에 배정한다. 코드 작성 중 새 색 처리·저장 호환·상태 구조 설계가 필요하면 Sol은 그 부분을 메인에게 돌린다. 메인은 최신 계약으로 답한다. 단순 답변이나 전달 비용이 더 큰 편집에 팀을 강제하지 않는다.

완료는 변경된 사용자 흐름과 생산자·소비자 경계가 해당 필수 검사를 통과하고, 기존 원본·데이터 보존이 확인된 상태다. 빌드 성공, 화면 조작, 실제 RW2 현상, S9 실기 결과는 각각 구분한다. 확인하지 못한 필수 검사는 `not_run`이며 완료로 바꾸지 않는다.

## 실행 계약

팀 실행 시 [런타임 가이드](../harness/references/runtime-guide.md)를 읽고 실제 제공 도구의 스키마를 확인한다. 런타임 장부는 Python 3.11 이상에서 프로젝트 루트 기준으로 실행한다.

- 각 작업은 `id`, `role`, `dependencies`, `ownership`, `inputs`, `context.decisions`, `context.skill_paths`, `acceptance`, `required`를 가진다. [작업·결과 형식](../harness/references/orchestrator-template.md)을 사용한다.
- `inputs`에는 변경하지 않을 계약·참조만 넣는다. 수정할 소스는 `ownership`에 넣고 입력과 겹치게 하지 않는다. 필요한 스킬을 `context.skill_paths`에 넣는다. 선행 출력은 처음부터 입력으로 넣지 말고 의존 작업의 승인 결과로 전달한다.
- 메인은 `init`/`resume` 전과 실제 배정 직전에 필수 `inputs`·`context.skill_paths`가 존재하고 읽을 수 있는지 확인한다. 런타임은 누락을 `missing` 지문으로 기록할 수 있으며 `ready`·`start`·완료 검사가 그 존재를 보장하지 않는다. 누락된 작업과 그 소비자는 배정을 보류하고 사유를 기록한다. 이미 시작한 작업은 `blocked`, 관련 필수 검사는 `not_run`으로 남긴다. 아직 생성하지 않은 작업에 가짜 ID를 등록하지 않는다. 입력이 준비되면 새 `resume` 실행의 패킷과 지문으로 재확인한다.
- 실제 프로젝트 경로와 고유 run ID를 선택해 `run.py init`으로 v2 장부와 최신 패킷을 만든다. 과거 run을 직접 수정해서 새 계약으로 덮어쓰지 않는다.

```sh
python3 .agents/skills/harness/scripts/run.py --project . init --plan-file .artifacts/feature-plan.json --run-id feature-v1
python3 .agents/skills/harness/scripts/run.py --project . ready --run feature-v1
```

위 계획 경로와 ID는 작업에 맞게 먼저 작성·선택한다. 이 명령은 에이전트를 생성하지 않는다.

## 배정과 협업

1. 실제 도구·모델·역할·동시 실행 한도를 확인한다. `.codex/agents/`의 TOML이 있다고 현재 세션에 자동 로드됐다고 가정하지 않는다. 역할 선택 인자가 없다면 해당 TOML을 읽어 지시로 전달하고 모델·effort를 실제 spawn 인자로 지정한다. 이 방식은 역할 자동 발견 검증과 구분한다. 모델 override를 지원하지 않으면 조용히 다른 모델로 대체하지 않는다.
2. 첫 자식 하나를 본 작업 없는 대기 상태로 생성한다. 실제 반환 ID를 확인한 뒤 첫 준비 작업에 재사용한다. `collab spawn failed: no thread with id`처럼 ID 없이 부모 조회가 실패하면 추가 생성을 멈춘다. 기존 메인에서 가능한 작업을 순차 수행하며 네이티브 작업은 `pending`으로 남긴다. 가짜 ID로 `start`하지 않는다.
3. 실제 자식 ID를 `run.py start --run RUN --task TASK --agent-id ACTUAL_ID`에 등록한 후 갱신된 `input.md`를 실제 후속 실행 도구로 전달한다. 본 작업 전에 패킷·입력 지문·계약 버전·필수 스킬·동료 ID와 책임을 읽고 수신 확인하게 한다.
4. 준비된 독립 쓰기 범위만 최대 3개 자식으로 넓힌다. 실제 런타임 한도가 더 작으면 그 한도를 따른다. 5개 역할을 항상 동시에 띄우지 않는다. 메인은 공통 계약과 통합을 맡고 자식은 재위임하지 않는다.
5. 같은 파일은 한 명만 수정한다. 특히 `LibraryModel.swift`와 `PhotoModels.swift`는 매 작업의 단일 소유자를 명시한다. 공유 코드를 바꿀 때는 계약 확정 → 코어 → 앱 소비자 → QA 순서를 지킨다. 준비된 입력으로 분리 가능한 UI 파일만 먼저 진행한다. 전체 Sources 디렉터리 소유권을 여러 명에게 나눠 주지 않는다.
6. 중요한 발견·질문·답변·차단·인계는 `communication.py`로 `_workspace/communications/`에 기록한 후 실제 도구로 전달한다. 전송 결과는 `sent`/`failed`, 실제 수신은 `received`로 원래 이벤트 ID와 연결한다. 읽기 전용 리뷰어의 기록은 메인이 대신한다. 로그 작성은 메시지 전송이나 수신 확인이 아니다.
7. 작업자는 첫 편집·단계 전환·완료 전 새 메시지의 본문까지 읽는다. 메인만 계약과 소유권을 변경한다. 작업 결과를 받았어도 실제 유휴·중단 상태를 확인하기 전 다른 작성자에게 소유권을 넘기지 않는다. `interrupt_agent`는 중단이며 종료와 다르다.

패킷의 파일 지문은 `run_support.snapshot_inputs`가 종류 접두사 등을 포함해 계산한다. `shasum`으로 얻은 원본 파일 SHA256과 그대로 비교하지 않는다. 이미지 원본 보존 검사에는 실제 파일 bytes의 SHA256을 사용한다.

## 통합과 검증

- 메인은 산출물의 diff와 계약을 직접 검토한다. 상태 모델, 저장 호환, 색 공간 등 중요한 변경은 `lighthouse_reviewer`의 독립 검토를 선택한다. 실행이 필요한 검사는 `lighthouse_qa`에 배정하거나 메인 Astra가 수행한다. QA는 제품 코드를 고치지 않는다.
- [검증 기준](references/verification.md)에서 변경에 맞는 최소 검사를 선택한다. `.build/`, `dist/`, 테스트용 카탈로그·이미지를 공유하는 명령은 메인이 한 번에 한 담당자에게 배정한다. 여러 작업자가 같은 전체 빌드를 반복하지 않는다.
- `LIGHTHOUSE_DATA_DIR`를 고유 임시 경로로 지정한다. 실제 사용자 카탈로그로 회귀 검사를 하지 않는다. 개인 사진·RW2·생성 LUT·카탈로그·상세 실행 로그는 Git에 추가하거나 외부로 보내지 않는다.
- 완료 결과는 `run_id`, `task_id`, `status`, `summary`, `artifacts`, `checks`, `issues`를 포함한다. 각 검사에 `required`, `status`, 실제 `evidence`와 실행한 경우에만 `command`를 기록한다. 결과·장부를 포함한 디렉터리 전체를 artifact로 지정하지 않는다.
- `run.py result`로 결과를 등록하고 실제 세션 상태를 별도 기록한다. 승인 산출물을 후속 작업이 수정하면 관련 결과와 소비자를 다시 검증한다. 읽기 전용 리뷰는 파일을 쓰게 하지 말고 메인이 메시지를 기록한다.
- 통합 후 `validate.py --project . --run RUN --complete`로 필수 결과·산출물·입력 최신성을 검사한다. 실제 최종 기능 검사도 따로 확인한다. 커밋·푸시는 사용자가 허용한 범위에만 수행하고 작업자에게 자동 권한을 주지 않는다.

## 오류와 재개

일시적인 도구 실패는 원인 확인 후 기본 1회만 추가 시도한다. 부모 스레드 사전 점검 실패에는 역할별 반복 생성을 하지 않는다. QA 수정은 기본 최대 2회로 두고, 남은 필수 실패는 실패로 보고한다. 타임아웃만으로 정상 작업을 중단하거나 침묵을 승인·성공으로 해석하지 않는다.

같은 주제의 후속 작업은 실제 유휴가 확인된 작업자에게 새 패킷으로 배정한다. `run.py resume --run OLD --new-run NEW`는 입력·계약·산출물이 바뀐 작업과 소비자를 다시 준비한다. 계약·소유권·작업 구성이 바뀌었다면 새 계획을 작성해 `--plan-file`로 전달한다. 이전 실행 기록을 보존한다. 재사용된 결과도 최신성을 확인하고, 사용한 모델·네이티브 역할 인식·UI·카메라 중 관찰하지 못한 사실은 미검증으로 기록한다.

## 하네스 유지보수

역할·경로·모델 정책을 바꾸면 팀 표, TOML, AGENTS 포인터와 `scripts/test-harness.py`의 정책 검사도 함께 검토한다. 하네스 구조 변경에는 다음을 실행한다. 앱 코드가 바뀌지 않았다면 Swift 전체 검사나 앱 재시작을 강제하지 않는다.

```sh
python3 .agents/skills/harness/scripts/validate.py --project .
python3 scripts/test-harness.py
```

정상 독립 작업 → 인계 → 독립 검토는 실제 네이티브 도구로 확인한다. 오류·소유권 충돌·변경 입력 재개는 임시 프로젝트에서 검증한다. fixture ID로 수행한 장부 회귀 검사를 실제 에이전트 생성·메시지 전달 성공으로 보고하지 않는다. 자동 스킬 선택은 새 세션에서 관찰한 경우에만 확인됐다고 말한다.
